เมื่อก่อนเวลาเราจะรัน Shellcode ในหน่วยความจำ เรามักจะใช้ API อย่าง `VirtualAlloc` หรือ `VirtualAllocEx` เพื่อสร้างพื้นที่ว่างขึ้นมาใหม่ ปัญหาคือ ในระดับ Windows Internals คือ การทำแบบนี้ระบบปฏิบัติการจะสร้างหน่วยความจำประเภท **`MEM_PRIVATE`** ขึ้นมา มันคือหน่วยความจำลอยๆ ที่ไม่มีไฟล์อ้างอิงอยู่เบื้องหลัง

ที่นี่เมื่อ Memory Scanner ของ EDR เริ่มสแกนแบบ Heuristic มันจะมองหาพื้นที่ `MEM_PRIVATE` ที่มีสิทธิ์เป็น `PAGE_EXECUTE_READ` หรือ `PAGE_EXECUTE_READWRITE` ทันทีที่เจอมันจะถือว่าเป็น Indicator of Compromise (IoC) เพราะโปรแกรมปกติแทบจะไม่มีการรันโค้ดจาก Memory เปล่า ๆ แบบนี้ แล้ว Shellcode ก็จะโดน Terminate Process ไปในที่สุด

ดังนั้น Module Stomping คือแทนที่เราจะจองหน่วยความจำแบบ Private เราจะไปขโมยเอาพื้นที่ของ DLL ที่ระบบปฏิบัติการโหลดและมี Trust ไว้เรียบร้อยแล้ว เช่น `kernel32.dll`, `user32.dll` หรือ DLL เฉพาะทางอื่นๆ
### 1. กระบวนการทำงานเบื้องต้น

1. หา DLL ที่ถูกโหลดอยู่ใน Process อยู่แล้ว และเลือกฟังก์ชันที่เป็น Export Function ขนาดใหญ่ที่โปรแกรมเหยื่อ ไม่น่าจะเรียกใช้งาน ในขณะนั้น

2. ใช้ `NtProtectVirtualMemory` เปลี่ยนสิทธิ์หน่วยความจำตรงฟังก์ชันนั้นจาก RX เป็น RW 

3. เขียน Shellcode ของเราทับลงไปบนพื้นที่ของฟังก์ชันนั้น เราเรียกตรงนี้ว่า Stomping

4. ปรับสิทธิ์กลับเป็น RX และสั่งรัน

พื้นที่ที่เราเขียนทับลงไปมีสถานะเป็น **`MEM_IMAGE`** ซึ่งหมายความว่า Kernel จะบันทึกว่าโค้ดส่วนนี้มีที่มาจากไฟล์ `.dll` ที่ถูกต้องบน Harddisk เมื่อ EDR สแกน Memory มาเจอก็จะเห็นแค่เนื้อหาของ DLL ระบบ ทำให้สามารถ Bypass การตรวจจับประเภท Unbacked Memory ได้อย่างสมบูรณ์แบบ

หาก EDR พยายามทำ Stack Trace ตอนที่ Shellcode ของเรากำลังทำงาน ตัว Instruction Pointer (`RIP`) จะชี้ไปที่ที่อยู่ในช่วงของ DLL มาตรฐานภายในเครื่อง ดูสมเหตุสมผลกว่าการที่ `RIP` ชี้ไปที่ Address แบบ Unbacked Memory เถื่อนที่อธิบายที่มาไม่ได้

สาระสำคัญของการหาไฟล์ .dll ที่จะนำมาใช้คือ ต้องมีขนาดใหญ่กว่า Loader ที่เราจะไปใช้เสมอ ไม่เช่นนั้นเมื่อเราทำการ Stomping ลงไปแล้วจะทำให้เกิด Stack Overflow และ Loader รวมถึงโปรแกรมเหยื่อจะหยุดทำงาน เครื่องของเป้าหมายจะรู้ตัวทันทีว่าเกิดการโจมตี
### 2. ขั้นตอนการทำงานของ Module Stomping

1. ทำการค้นหา PID ของโปรเซสเป้าหมาย เช่น `discord.exe` หรือ `explorer.exe` และเปิด Handle ผ่าน Native API เพื่อไม่ให้ถูกดักจับที่ชั้น Win32 API

   สำหรับ PoC นี้ เราจะใช้ Native API โดยตรงเพื่อความง่าย

2. เลือก DLL มาตรฐานที่ทุกโปรเซสต้องโหลด โดยในที่นี้เลือกใช้ `kernel32.dll` และเลือกฟังก์ชันที่เป็น **Export Function** ขนาดใหญ่และไม่ค่อยถูกใช้งาน จะใช้ `GetDateFormatW` เพื่อไว้ใช้เป็นที่พักของ Shellcode

   เมื่อ OS โหลด Process ขึ้นมา โครงสร้าง VAD หรือ Virtual Address Descriptor ใน Kernel จะบันทึกว่าหน่วยความจำส่วนนี้เป็น `MEM_IMAGE` หรือที่แปลว่า มีไฟล์บนฮาร์ดดิสก์รองรับ

   โดยที่เราเลือก `GetDateFormatW` เป็นเพราะ ฟังก์ชันนี้มีจำนวนไบต์มากพอที่จะยัด Shellcode ของเราลงไปได้ และ โปรเซสอย่าง Discord หรือ Explorer แทบจะไม่ได้เรียกใช้ฟังก์ชันจัดการรูปแบบวันที่ใน Background การเลือกฟังก์ชันที่ไม่ถูกเรียกใช้งาน จะช่วยป้องกันสภาวะ Race Condition ที่โปรเซสเหยื่ออาจเรียกใช้ฟังก์ชันนี้ในจังหวะที่เรากำลังเขียนทับ ซึ่งจะทำให้เกิด Access Violation ทันที

3. เปลี่ยนสิทธิ์หน่วยความจำจาก Read-Execute (RX) เป็น Read-Write (RW) ผ่าน **`NtProtectVirtualMemory`** เฉพาะจุดที่จะเขียนทับ เพราะโดยปกติ `MEM_IMAGE` จะถูกตั้งค่าเป็น `PAGE_EXECUTE_READ` (RX) เพื่อป้องกันการแก้ไขโค้ด

   เราจะใช้ `NtProtectVirtualMemory` เปลี่ยนสิทธิ์เป็น `PAGE_READWRITE` (RW) เพราะกลไก Kernel Callback ของ EDR อย่าง ETW-Ti จะมอนิเตอร์การเปลี่ยนสิทธิ์เป็น RWX การปรับเป็น RW จะดูเหมือนการแก้ไขข้อมูล Data ปกติในหน่วยความจำ ลดความน่าสงสัยของ EDR

4. ก่อนทำการเขียนทับ ทำการดูดข้อมูลดั้งเดิมออกมาเก็บไว้ใน Heap ของ Process เราเองก่อน เพื่อใช้ในการกู้คืนภายหลัง เป็นแนวทางปฏิบัติที่ปลอดภัยที่สุด เพื่อป้องกัน Heap Corruption เราจะใช้ Native Windows Heap อย่าง `HeapAlloc` แทนที่จะใช้ `new/delete` ของ C++ ทั่วไป และมันยังช่วยให้ Memory ของโปรเซสเป้าหมายไม่เกิดอาการผิดปกติจากการจองพื้นที่แปลก จนอาจ Crash ได้
   
5. นำ Shellcode ที่ผ่านการทำ Stack Alignment หาร 16 ลงตัว และตั้งค่า `EXITFUNC=thread` เขียนลงไปทับฟังก์ชันเป้าหมายในโปรเซสเหยื่อด้วย `NtWriteVirtualMemory` โดยในการเขียน จำเป็นต้องเรียก `NtProtectVirtualMemory` อีกครั้งเพื่อปรับสิทธิ์จาก RW กลับไปเป็น **RX** ก่อนที่จะสั่ง Execute 

6. สั่งทำงาน Shellcode โดยการสร้าง Thread ใหม่ด้วย `CreateRemoteThread` ชี้ไปที่จุดที่เขียนทับไว้ เมื่อใช้งานแล้ว ระบบปฏิบัติการจะสร้าง Thread ใหม่ โดยมี `lpStartAddress` ชี้ไปที่ฟังก์ชันเป้าหมาย

   เมื่อกลไก `PsSetCreateThreadNotifyRoutine` ใน Kernel ตรวจจับการสร้าง Thread มันจะเช็คที่อยู่เริ่มต้น มันจะพบว่า Thread นี้เริ่มต้นทำงานจากเขตแดนที่ถูกต้องของ `kernel32.dll` ไม่ใช่หน่วยความจำแบบ Unbacked Memory หรือ `MEM_PRIVATE` (หรือ Private_Commit) ทำให้มันดูเหมือนการแตก Thread ปกติของระบบ

7. เมื่อ Shellcode ทำงานเสร็จสิ้น ตัว Loader ของเราจะทำการเขียนไบต์ดั้งเดิมทับกลับลงไปและคืนสิทธิ์หน่วยความจำให้เป็น RX ตามเดิม เพื่อให้ Memory Scanner ตรวจไม่พบความผิดปกติ

# สรุปว่าเกิดอะไรขึ้นบ้าง

   หากงง หัวข้อนี้จะสรุปขั้นตอนการเปลี่ยน Protection ตั้งแต่ขั้นที่ 2 จนถึงขั้นที่ 7 ว่ามันเปลี่ยน Protection กันไปกี่ครั้ง แล้วเปลี่ยนเป็นอะไรไปบ้าง

   #### รอบที่ 1 RX $\rightarrow$ RW

   โครงสร้าง VAD ของ `kernel32.dll` ใน Process เหยื่อ เดิมทีจะถูกมาร์กไว้เป็น `PAGE_EXECUTE_READ` (RX) ดังนั้นเราเลยต้องสั่งเปลี่ยนเป็น `PAGE_READWRITE` (RW) ก่อน เพื่อให้ฟังก์ชัน `NtWriteVirtualMemory` สามารถยัดไบต์ของ Shellcode ทับลงไปที่พิกัดของ `GetDateFormatW` ได้โดยไม่โดน Access Violation (0xc0000005)

   #### รอบที่ 2 RW $\rightarrow$ RX

   ตรงนี้ EDR/Sysmon จะดักจับการใช้ `CreateRemoteThread` แบบผิดปกติ ถ้าเราให้ Thread ใหม่ที่เราสร้างมาชี้ไปที่หน่วยความจำที่เป็นแบบ RWX ระบบจะ Alert ทันที เราเลยเปลี่ยนกลับเป็น RX ทำให้ตอนที่ Instruction Pointer `RIP` เริ่มทำงาน โครงสร้าง Memory จะดูเหมือนโค้ดของ `kernel32.dll` 100%

   #### รอบที่ 3 RX $\rightarrow$ RW

   หลังจาก `WaitForSingleObject` แจ้งว่า Shellcode ทำงานจนจบและ Thread ตายไปแล้ว เราต้องทำ Shellcode ของเราที่ค้างอยู่เพื่อลบหลักฐาน ก็เลยต้องเปิดสิทธิ์เป็น RW อีกครั้ง เพื่อให้สามารถใช้ `NtWriteVirtualMemory` เอาตัว `originalBytes` ที่ Backup ไว้ใน Heap ฝั่งเรา ไปเขียนทับ Shellcode คืน

   #### รอบที่ 4 RW $\rightarrow$ RX

   การเขียน Original bytes ลงไปอย่างเดียวยังไม่เนียนพอ แบบที่กล่าวไปในรอบแรก โค๊ดแบบ Executable มันเป็น RX ตั้งแต่แรก เราจึงเปลี่ยนสิทธิ์กลับเป็น ซึ่งก็คือ RX เป็นครั้งสุดท้าย เพื่อให้ Memory ของ Process เหยื่อแปลงร่างกลับเป็นเหมือนเดิมเหมือนตอนที่ OS เพิ่งโหลดมันขึ้นมาครั้งแรก

   #### สรุป

   1. RW เพื่อเขียน Shellcode
   
   2. RX เพื่อสั่งทำงาน
   
   3. RW เพื่อเขียน Backup คืน
   
   4. RX เคลียร์ประวัติไม่ดี ปิดงาน
